= Boost.Decimal TOMS Paper: Writing Plan
:idprefix: writing_plan_
:toc: left

This is the working plan for researching and writing the Boost.Decimal paper for
ACM Transactions on Mathematical Software (TOMS). It spans several drafting and
revision sessions, so it is meant to be re-read at the start of each one. It maps
every paper section to concrete source material already in the library, names an
exemplar accepted paper to model each section on, and tracks status with
checkboxes.

Companion files in this folder:

* `research.adoc`: the venue and journal research, and the reasoning for targeting
  TOMS as a research paper (not an Algorithms paper) and opting into Replicated
  Computational Results (RCR).
* `paper/toms_decimal.tex`, `paper/references.bib`, `paper/Makefile`: the
  compilable `acmart` (`acmsmall`/TOMS) scaffold. It builds against the unmodified
  `acm/template/` folder.

== Locked decisions

* *Thesis and spine:* Portability, constexpr, and GPU. One header-only C++14 source
  that is conformant and consistent across CPU, GPU (CUDA), and bare metal, at both
  compile time and run time, with performance parity or improvement over the Intel
  reference. Primary structural model: FloatX.
* *Featured optional sections:* (1) exact decimal I/O via Ryu plus charconv
  conformance, and (2) an applications section on Boost.Math composability (the
  integration that lets the existing C++ numerical ecosystem operate on decimal data),
  with a financial dataset as the worked example.
* *Demoted to brief subsections:* the special functions suite and the `sqrt`
  algorithm deep dive. Both are referenced, neither gets its own section.
* *Article type and length:* TOMS research paper, `acmsmall` format, target 18 to 24
  pages. Opt into RCR.

== Contributions (Section 1 must state these explicitly)

. Header-only, dependency-free C++14 implementation of IEEE 754 decimal32, decimal64,
  and decimal128, plus three speed-tuned non-conforming variants.
. Full constexpr (compile time) decimal arithmetic.
. GPU and CUDA execution from the same source as the CPU path: to
  our knowledge the first decimal floating-point library with GPU support.
. Verified cross-platform, bit-for-bit consistent results across x86-32, x86-64,
  ARM32, ARM64, s390x (big-endian), PPC64LE, and bare-metal ARM Cortex-M.
. Exact, conformant decimal I/O (shortest round-trip via Ryu) and BID/DPD support.
. A performance study showing parity with or improvement over Intel BID and GCC
  `_Decimal` across the basic operations on multiple platforms.

NOTE: Keep every novelty claim hedged exactly as in `research.adoc`. The formats,
the BID encoding, and IEEE 754 conformance are prior art; the novelty is the
portability envelope, the compile-time guarantee, and GPU capability delivered
together. State the GPU claim as "first decimal floating-point library with GPU
support that we are aware of."

== Global conventions

* All prose is ASCII only. No em dashes, no en dashes, no double-hyphen prose
  punctuation. Use colons, parentheses, or split sentences.
* The draft lives in `paper/toms_decimal.tex` (renamed from the original outline once it
  became a full draft). Always build against the untouched `acm/template/`.
* Do not commit build artifacts (PDF, aux files). Keep sources only.
* End each session with a clean `make` build and tick the relevant status boxes
  below.

== Section-by-section plan

Each section lists its purpose, key content, the documentation and code to draw
from, what is new work versus adaptable from existing prose, the exemplar to model
on, a rough page budget, and a status box.

=== 1. Introduction

* [x] Drafted   [x] Revised
* *Purpose:* motivate decimal, state the gap, list the contributions.
* *Key content:* binary cannot store values like 0.1 or 0.3 exactly, so error
  enters as early as parsing a price; show the 0.1 + 0.2 example and the decimal64
  result. The gap: Intel and IBM are C libraries, not header-only, with no constexpr,
  no GPU, and partial architecture coverage. State the six contributions. Add the
  honest scope note.
* *Sources (docs):* `overview.adoc`, `decimal_float_and_sqrt.md` (the 0.1 example
  and bit layout), and the Novelty section of `research.adoc`.
* *New vs adapt:* mostly adaptable from existing prose.
* *Model:* MPFR and FloatX introductions.
* *Target:* about 1.5 pages.

=== 2. Background and Related Work

* [x] Drafted   [x] Revised
* *Purpose:* establish prior art and position Boost.Decimal against it.
* *Key content:* IEEE 754 decimal formats and precisions (7, 16, 34 digits); BID
  versus DPD encodings; prior implementations (Intel RDFP/libbid, IBM decNumber, GCC
  libdecnumber/libbid, HP); ISO/IEC TR 24733 and WG21 N3407/N3871 and their plan to
  wrap the C libraries with optional constexpr; cuDF GPU decimal is fixed point, not
  IEEE 754 DFP. Build the feature-comparison table (header-only, language, constexpr,
  GPU, architectures, license) across Boost.Decimal, Intel, IBM, GCC.
* *Sources (docs):* `conversions.adoc`, `cohorts.adoc`.
* *Sources (refs):* cornea2009, intel-dfp, ibm-decnumber, tr24733, wg21-n3407,
  wg21-n3871, nvidia-cudf (all in `references.bib`).
* *New vs adapt:* the comparison table is new; the prose adapts `research.adoc`.
* *Model:* MPFR related work.
* *Target:* about 2 pages.

=== 3. Design and Architecture

* [x] Drafted   [x] Revised
* *Purpose:* explain the design goals and how the library is structured.
* *Key content:* goals in priority order (ease of use, portability, performance);
  the six types and the conforming-versus-fast tradeoff; header-only C++14 with a
  clang-6 floor; standard-library integration surfaces; BID storage and layout; the
  constexpr strategy and how it composes with the GPU path.
* *Sources (docs):* `design.adoc` (rationale and acknowledged deviations),
  `fast_types.adoc`, `generic_decimal.adoc`, `limits.adoc`, `decimal32_t.adoc`,
  `decimal64_t.adoc`, `decimal128_t.adoc`.
* *Sources (code):* `include/boost/decimal/decimal32_t.hpp`, `decimal64_t.hpp`,
  `decimal128_t.hpp`, `decimal_fast32_t.hpp`, `decimal_fast64_t.hpp`,
  `decimal_fast128_t.hpp`, `detail/config.hpp`, `detail/bit_layouts.hpp`,
  `detail/concepts.hpp`, `detail/type_traits.hpp`.
* *New vs adapt:* mostly adaptable from `design.adoc` and `fast_types.adoc`.
* *Model:* FloatX and Algorithm 910.
* *Target:* about 2.5 pages.

=== 4. Arithmetic Implementation

* [x] Drafted   [x] Revised
* *Purpose:* describe how the core operations are implemented.
* *Key content:* construction and normalization; add and subtract (exponent
  alignment, rounding); multiply (wide-integer product); divide; rounding modes and
  the floating-point environment; special values and total ordering; the bundled
  int128 and u256 backend. Two brief subsections, not featured: `sqrt` (SoftFloat-
  inspired reciprocal-sqrt table plus Newton-Raphson) and the special functions
  suite, each a short paragraph that points at the implementation.
* *Sources (code):* `detail/add_impl.hpp`, `detail/mul_impl.hpp`, `detail/div_impl.hpp`,
  `detail/mod_impl.hpp`, `detail/fenv_rounding.hpp`, `detail/comparison.hpp`,
  `detail/normalize.hpp`, `detail/int128/detail/common_mul.hpp`, `common_div.hpp`,
  `int128_imp.hpp`, `uint128_imp.hpp`, `detail/u256.hpp`. For the `sqrt` subsection:
  `decimal_float_and_sqrt.md` plus `detail/cmath/impl/sqrt32_impl.hpp`,
  `sqrt64_impl.hpp`, `sqrt128_impl.hpp`. For special functions:
  `detail/cmath/` and `detail/cmath/impl/`.
* *New vs adapt:* adapt the `sqrt` writeup; new prose for add, multiply, divide.
* *Model:* MPFR algorithms section.
* *Target:* about 3 pages.

=== 5. Exact Decimal I/O and Conformant Conversion (FEATURED)

* [x] Drafted   [x] Revised
* *Purpose:* exact base-ten I/O is the point of decimal; show it is done correctly
  and fast.
* *Key content:* shortest round-trip via the Ryu algorithm; the `chars_format`
  options including `cohort_preserving_scientific`; BID and DPD conversions; cohorts
  (multiple representations of one value) and how they are handled; round-trip
  guarantees and the deliberate LWG-3081 deviation (distinguishing overflow from
  underflow).
* *Sources (docs):* `charconv.adoc`, `conversions.adoc`, `cohorts.adoc`, `format.adoc`.
* *Sources (code):* `charconv.hpp`, `detail/ryu/ryu_generic_128.hpp`,
  `detail/ryu/generic_128.hpp`, `bid_conversion.hpp`, `dpd_conversion.hpp`,
  `detail/parser.hpp`, `detail/from_chars_impl.hpp`, `detail/to_chars_integer_impl.hpp`.
* *Sources (refs, to add):* Ryu (Adams, PLDI 2018, doi 10.1145/3192366.3192369).
* *New vs adapt:* adapt `charconv.adoc` and `conversions.adoc`; add the Ryu citation.
* *Model:* FloatX and MPFR on correctness.
* *Target:* about 2.5 pages.

=== 6. Portability and Cross-Platform Consistency

* [x] Drafted   [x] Revised
* *Purpose:* show one source runs everywhere and gives identical results.
* *Key content:* the operating-system and architecture matrix (Linux, Windows,
  macOS across x86-32, x86-64, ARM32, ARM64, s390x, PPC64LE, bare-metal Cortex-M);
  big-endian s390x handling; avoiding compiler-specific decimal or 128-bit

* *Sources (code and config):* `detail/config.hpp` (endianness, int128 and CUDA

* *New vs adapt:* a clean CI and architecture table is new.
* *Model:* MPFR portability discussion.
* *Target:* about 2 pages.

=== 7. GPU and Accelerator Support

* [x] Drafted   [x] Revised

=== 8. Conformance and Verification

* [x] Drafted   [x] Revised
* *Purpose:* establish correctness; anchor the RCR case.
* *Key content:* IEEE 754 conformance and the acknowledged deviations (non-Clause-5
  cmath functions are not correctly rounded, matching Intel); the industry-standard
  dectest suite (submodule, the parser and runner harness, per-operation coverage);
  property-based and fuzz testing; the GitHub-issue regression tests.
* *Sources (code):* `test/decimal-dectest/test_harness.hpp` and
  `test/decimal-dectest/dectest/*.decTest`, `fuzzing/fuzz_*.cpp`,
  `test/github_issue_*.cpp`, plus the deviations listed in `design.adoc`.
* *New vs adapt:* a dectest pass-count summary table per operation and type is new.
* *Model:* MPFR (correct rounding) and CPFloat (correctness validation).
* *Target:* about 2 pages.

=== 9. Performance Evaluation

* [x] Drafted   [x] Revised
* *Purpose:* quantify the performance story honestly.
* *Key content:* methodology (the random-vector harness, repeated runs, and the
  C-versus-C++ fairness caveat); hardware and toolchains; baselines (Intel BID, GCC
  `_Decimal`, IBM decNumber if buildable, and `double` as the hardware reference);
  headline results, for example `decimal_fast64_t` addition about 4.6x faster than
  Intel `BID_UINT64` on x64 with the Intel compiler, and the larger 128-bit multiply
  gap; honest framing ("faster across the basic operations," not "fastest");
  per-operation, per-platform tables and figures.
* *Sources (docs):* `benchmarks.adoc`.
* *Sources (code):* `test/benchmarks.cpp`, `test/benchmark_libbid.c`,
  `test/benchmark_libdfp.c`, `test/benchmark_uint256.cpp`.
* *New vs adapt:* re-run the matrix for the camera-ready on documented hardware and
  regenerate every table. See "New empirical work" below.
* *Model:* BLASFEO, CPFloat, FloatX.
* *Target:* about 3 pages.

=== 10. Applications: Composability with Boost.Math (FEATURED)

* [x] Drafted   [x] Revised
* *Purpose:* show the real applications payoff: because the types are standards-conforming
  C++ types, the existing C++ numerical ecosystem (Boost.Math) operates on exact decimal
  data with no new code. This is the genuinely novel impact point (the C reference
  libraries cannot compose this way), not a base-ten arithmetic demo.
* *Key content:* exact input from real market data (decimal32_t sum 52151.99 matches the
  spreadsheet, float gives 52151.96); Boost.Math `statistics::{mean,median,variance}` on a
  `vector<decimal64_t>` to compute Bollinger bands (mean $207.20, std dev $25.45, bands
  $258.11 / $156.30); the breadth tested in CI (full univariate-statistics suite, plus
  special functions beta/zeta/ellint/legendre/laguerre/hermite); the generic-programming
  argument for why this is free and why a C library cannot be dropped in.
* *Sources (docs):* `financial_examples.adoc`, `design.adoc` (Boost.Math integration).
* *Sources (code and data):* `example/statistics.cpp`, `example/numerical_parsing.cpp`,
  `example/AAPL.csv`; the CI evidence `test/test_boost_math_univariate_stats.cpp` and the
  special-function tests that include `boost/math/...`.
* *New vs adapt:* mostly write-up of an already-implemented and tested integration. Only
  optional fresh work: re-run cross-architecture to confirm identical results.
* *Model:* FloatX case studies (validation through real use).
* *Target:* about 2 pages.

== Risks and levers

* *Page budget versus twelve sections.* If the draft runs long, fold Section 5 into
  Section 4 and Section 11 into Section 12. These are deliberate cut levers, not
  silent omissions.
* *Benchmark fairness.* The C baselines are benchmarked against C++ types; address
  this explicitly in the methodology. The note already in `benchmarks.adoc` is the
  starting point.
* *IBM decNumber baseline.* Depends on `test/benchmark_libdfp.c` building in the
  test environment; treat as optional.
* *Complementary ARITH submission.* The arithmetic-focused angle could go to ARITH
  (IEEE Xplore) as a separate, non-overlapping publication. Out of scope for this
  plan; noted in `research.adoc`.

* All twelve sections and Appendix A have both status boxes ticked.

  the paper.

* `make` in `paper/` produces a clean PDF within the page budget against the
